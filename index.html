What this API is

It runs the shipped statements of a named console screen. A caller names a console, a screen, a statement index and the bind values; the console looks the statement up in the catalogue decoded from the vendor's own console forms and runs it with those values bound as parameters.

It is not a general SQL endpoint. No parameter carries SQL, and the binds go to the driver as query parameters, so a caller cannot inject a statement. A caller can only run what the vendor shipped, and only on the screen the vendor shipped it for.

A service that needs arbitrary SQL, or the configuration at scale, should read the platform's database directly with its own least-privilege login. This API is the operator surface.

Authentication

Two ways in.

Database login: the machine-friendly one

The shipped consoles' own sign-in is a database login, so this API checks the operator's credentials against the platform's database. It is the method a service should use.

bash 
curl -s -c cookies.txt -X POST https://postilion-sim.novustech.dev/api/login \
  -H 'Content-Type: application/json' \
  -d '{"operator_id":"uopviewer","password":"<password>"}'

The answer sets a session cookie, postilion_console. Send it on every later call:

http 
Cookie: postilion_console=<value>

Keycloak SSO: for people

The browser redirect flow at /api/auth/login, with the callback at /api/auth/callback. It exists so an operator does not need a second password. It is a browser flow: it needs a human at the keyboard, so a service must not use it.

Sessions

  • A session lives in the console pod's memory, for 8 hours of inactivity.
  • A pod restart (a rollout, a node drain, an eviction) drops every session. A service must treat 401 as "sign in again", not as "the request was wrong".
  • The console runs one replica, so there is one session store.

Rights

Rights are read from the database, from the roles the principal holds:

Role held by the loginRights
db_owner, db_datawriter, postapp, postcfg readwrite
db_datareader, postmon, postaud read
anything elseread

A read-only principal is refused by the write endpoint with 403, and the console says so in the operator badge. The platform's own service logins (upostapp, upostmon, upostcfg, upostaud) are not for services: they belong to the platform's services.

Errors

Every failure is the same shape: {"detail": "..."}, or {"detail": {...}} for the write confirmation. A 404 names the missing object, a 400 names the reason the statement was refused, and a 409 is the write asking for confirmation.

In detail

GET /api/consoles

The console tree. The shipped menu path is the tree, because that is how an operator knows the platform.

json 
{"consoles": [
  {"name": "Config - Cards", "menu_path": "Config - Cards",
   "group": "Config", "component": "TConfigCards",
   "purpose": "...", "screen_count": 32, "statement_count": 63}
]}

GET /api/console/{console}

One console, its screens, and every statement on each screen with the statement's index, kind, verb and bind names.

json 
{"console": {"name": "...", "menu_path": "...", "group": "...",
              "purpose": "...", "component": "..."},
 "screens": [
   {"form": "TConfigCards", "caption": "...", "grids": [...], "values": [...],
    "binds": [...], "buttons": [...],
    "statements": [{"index": 0, "kind": "read", "verb": "select",
                    "sql": "SELECT ... :NAME ...", "binds": ["NAME"],
                    "tables": ["..."]}]}
 ]}

The index of a statement is what /api/query and /api/write take. Indices are the statement's position within its screen: the reads first, in shipped order, then the writes.

POST /api/query

json 
{"console": "Config - Cards", "screen": "TConfigCards", "statement": 0,
 "params": {"NAME": "value"}, "limit": 500, "offset": 0}

params supplies the statement's binds, by name. A bind with no value is an error (400 missing value for :NAME): the console never guesses a NULL.

json 
{"rows": [{"COLUMN": "value"}], "returned": 12, "total": 12,
 "columns": ["COLUMN"], "sql": "SELECT ..."}

limit and offset page the rows. total is the number of rows the statement returned, before paging.

POST /api/write

The same shape, plus the confirmation:

json 
{"console": "...", "screen": "...", "statement": 12,
 "params": {"NAME": "value"}, "confirm": false, "target": "optional note"}

Without confirm, the write is refused with 409 and the console says what it would have done:

json 
{"detail": {"message": "confirmation required", "action": "UPDATE",
            "statement": "UPDATE ...", "target": "NAME"}}

The caller then repeats the request with "confirm": true. The answer:

json 
{"ok": true, "action": "UPDATE", "rows_affected": 1}

Every write is journalled in the platform's console_audit_log with the operator, the console, the screen, the action, the target and the number of rows. GET /api/audit?limit=100 reads it back.

GET /api/audit

json 
{"audit": [{"audit_id": 12, "audit_time": "2026-11-16 09:12:44.000",
            "operator_id": "uopadmin", "operator_name": "uopadmin",
            "console_name": "...", "screen_name": "...",
            "action_name": "UPDATE", "target_key": "...", "rows_affected": 1}]}

From another service

Give the service its own principal

One login per service, named for the service, with the least privilege it needs. A service that only reads gets a db_datareader member; a service that must change configuration gets a postapp member. Do not hand a service a human's credentials, and do not use the platform's own upostapp login, which the platform's services also use.

Keep the session, and sign in again when it ends

python 
import json, urllib.error, urllib.parse, urllib.request, http.cookiejar

BASE = "https://postilion-sim.novustech.dev"

class Console:
    """A session against the Postilion operator console."""

    def __init__(self, base=BASE, operator=None, password=None):
        self.base = base
        self.operator = operator
        self.password = password
        self.jar = http.cookiejar.CookieJar()
        self.opener = urllib.request.build_opener(
            urllib.request.HTTPCookieProcessor(self.jar))

    def login(self):
        body = json.dumps({"operator_id": self.operator,
                            "password": self.password}).encode()
        req = urllib.request.Request(
            self.base + "/api/login", data=body, method="POST")
        req.add_header("Content-Type", "application/json")
        with self.opener.open(req, timeout=30) as r:
            return json.loads(r.read().decode())

    def call(self, path, payload=None, method=None):
        """One API call, signing in again once if the session has expired."""
        data = json.dumps(payload).encode() if payload is not None else None
        req = urllib.request.Request(
            self.base + path, data=data,
            method=method or ("POST" if data else "GET"))
        if data:
            req.add_header("Content-Type", "application/json")
        try:
            with self.opener.open(req, timeout=60) as r:
                return json.loads(r.read().decode())
        except urllib.error.HTTPError as e:
            if e.code == 401:
                # The pod was replaced and the session went with it.
                self.login()
                return self.call(path, payload, method)
            raise

    def query(self, console, screen, statement, **params):
        return self.call("/api/query", {"console": console, "screen": screen,
                                         "statement": statement, "params": params})

    def write(self, console, screen, statement, params, target=""):
        """A write, in two steps: ask, then confirm."""
        body = {"console": console, "screen": screen, "statement": statement,
                "params": params, "target": target}
        try:
            return self.call("/api/write", body)
        except urllib.error.HTTPError as e:
            if e.code != 409:
                raise
            detail = json.loads(e.read().decode()).get("detail", {})
            # A service may confirm automatically once it has decided what it
            # is changing. A human should read the target first.
            body["confirm"] = True
            return self.call("/api/write", body)

What to point a service at

The service needsUse
One configuration value GET /api/console/{console}, then POST /api/query with the statement's binds
A list of records POST /api/query, paging with limit and offset
To change configuration POST /api/write, confirm after reading the 409
To know who changed what GET /api/audit
Its own health GET /api/healthz (never touches the database)
To be ready GET /api/health (counts the platform's tables)

Notes for a service author

  • Statement indices are per screen. Discover them from GET /api/console/{console} rather than hard-coding them; a console's screens and statements come from the vendor's own form streams.
  • The catalogue is the vendor's. Screen and console names are the shipped names, and the API answers 404 for a name the vendor does not ship.
  • A write is journalled. The audit row names the operator, so a service should use its own principal: the trail then says which service changed what.
  • Do not cache a session across a restart. 401 is cheap to recover from and is the only signal that the pod changed.
  • There is no rate limit and no API key. The console sits behind the VPN and its audience is a handful of operators and a few services.
  • The API speaks JSON only. No CSV, no XML.

By hand

bash 
BASE=https://postilion-sim.novustech.dev

# sign in and keep the cookie
curl -s -c jar.txt -X POST $BASE/api/login \
  -H 'Content-Type: application/json' \
  -d '{"operator_id":"uopviewer","password":"<password>"}'

# what can I call
curl -s -b jar.txt $BASE/api/consoles | head -c 400

# the statements of one console
curl -s -b jar.txt "$BASE/api/console/Config%20-%20Cards" | head -c 400

# run its first read
curl -s -b jar.txt -X POST $BASE/api/query \
  -H 'Content-Type: application/json' \
  -d '{"console":"Config - Cards","screen":"TConfigCards","statement":0,
       "params":{}}' | head -c 400

# who changed what
curl -s -b jar.txt "$BASE/api/audit?limit=5"
Credentials

The operator passwords are not published here. They live in the deployment's own secret store, in secrets/kdev.env on the deployment host and in the operator's .env on the platform's guest. Ask the platform owner for the service principal your service should use, rather than reusing an operator's.

ISO 8583

The API above is HTTP over the platform's database. The platform's other surface is ISO 8583, and it is not HTTP: it is a binary TCP protocol that terminals, acquirers and scheme nodes speak. It is a different thing with a different shape, and this section is its contract.

Where it runs

WhatValue
Endpointiso.postilion-sim.novustech.dev, which is postilion-iso in the postilion namespace, a LoadBalancer on the Contabo segment. VPN only: the public edge does not serve it, and the public resolver does not answer the name.
Address10.10.30.209, port 18585, the cluster's ISO 8583 port
Serverthe shipped Sink injector: the vendor's own counterparty responder, on the platform's own codec and framing
Framingthe platform's Postilion header filter, on both ends
Messagesthe platform's own Iso8583Post codec

The framing

A frame is a length prefix and then the message:

wire
+---------------------------+--------------------------------------+
| 2B BE len | or FF FF      | payload: the ISO 8583 message       |
| (payload) | 4B BE len     |                                      |
+---------------------------+--------------------------------------+
  normal        >= 65535 bytes
  • Below 65535 bytes: a 2-byte big-endian length of the payload only.
  • At or above 65535 bytes: FF FF then a 4-byte big-endian length.
  • Nothing else travels in the header: no tracer, no node name, no sequence number. A counterparty whose specification expects a tracer will not find one.

The message

  • The MTI is four ASCII hex characters: "0110", not a decimal number.
  • The primary bitmap is 8 bytes, big-endian, bit 1 = field 1.
  • Bit 1 of the primary bitmap means "a secondary bitmap follows", and the secondary bitmap is the next 8 bytes with bit 1 = field 65.
  • The fields follow in ascending order.
  • A variable-length field carries its length as ASCII decimal digits before the value ("16" then 16 characters); a fixed field does not.
  • Field 127 is the platform's private sub-bitmap.

What the endpoint answers

You sendIt answersWith
0800 sign-on0810DE70 = 001, DE39 = 00; the original 0800 is echoed back afterwards
0100 authorisation0110DE39 = 00
0200 transaction0210DE39 = 00

DE70 = 301 on an 0800 is the echo test, and it is answered with DE70 = 301 and no approval.

Trying it by hand

tools/iso/iso_client.py is a plain client with no Postilion code in it: it speaks the framing and the message layout directly over a socket. That is deliberate, because a client built from the platform's own classes would only prove the platform agrees with itself. A successful exchange through this client is evidence that a third party can talk to the endpoint.

The frames it builds are checked against the platform's own recorded frames, byte for byte (sim/harness/golden/iso.exchange.txt), so the client cannot drift from the wire format:

bash
python3 tools/iso/iso_client.py --self-check
python3 tools/iso/iso_client.py iso.postilion-sim.novustech.dev 18585 --signon --auth

Expected output:

text
connected to iso.postilion-sim.novustech.dev:18585
sign-on: sent 0800 -> received 0810 (answer; fields 1,39)
sign-on: sent 0800 -> received 0800 (echo; fields 1)
authorisation: sent 0100 -> received 0110 (answer; fields 1,2,3,4,7,11,12,13,39,41,42,49)
closed

What this endpoint is not

It is not the platform's Transaction Manager listener, which is the switch's own transaction path. That one takes a terminal's or a scheme node's traffic into the platform proper, and it needs:

  • the link configuration as rows in the database, not as properties: node_saps (the endpoint: protocol, the ip,port address, the filter stack) and node_conns; the listener ports come from the node's interchange configuration;
  • the node, the source node and the sink node to exist as rows;
  • the Transaction Manager service to be running, which the deployment does not start today (only the Scheduler runs);
  • and, for a live node, the platform's licence to validate.

The console can write the configuration rows for you, because the node and SAP screens are in its catalogue: c_RealtimeApplications / TSAPEDITDLG (node_saps) and TEDITCONN (node_conns), and m_Postilion / TQRYSYSTEMOVERVIEW to read them back. The address format is ip,port with a comma, and a missing comma makes the whole string the port.

Sign-on between a node and the Transaction Manager

When the platform's own node talks to the Transaction Manager, that link is an ISO 8583 sign-on too, with its own rules:

Operations

  • Probes. /api/healthz for liveness and /api/health for readiness. The readiness check runs a query, so it is allowed 35 seconds.
  • The audit table is console_audit_log in the platform's realtime database, and the console creates it if it is missing.
  • The API version is the console's: the catalogue is regenerated from the shipped console forms, so a screen's statement indices move if the vendor's forms move.
  • Sign-ins are logged. Every SSO sign-in records the account, the rights granted and the roles the identity token carried.
